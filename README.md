# 🛒 Retail Sales SQL Audit & Analytics

A practical **MySQL SQL project** focused on analyzing and managing retail sales data using advanced SQL concepts such as **stored procedures, functions, triggers, transactions, JSON data, conditional aggregation, indexing, query optimization, joins, subqueries, temporary tables, and audit logging**.

This project demonstrates how SQL can be used not only for querying data, but also for **business analysis, data integrity, auditing, transaction management, and performance optimization**.

---

## 📌 Project Overview

The project uses a retail sales database called `mystore` and works primarily with the `store_sales` table.

The SQL scripts simulate real-world retail data operations such as:

* Employee sales performance analysis
* Revenue calculation
* Product attribute management using JSON
* Price-change auditing
* Transaction and rollback management
* Sales returns
* Category-wise revenue analysis
* Query performance optimization
* Index creation
* Database and table verification
* Joins and subqueries
* Temporary table operations
* SQL safe-update handling

The project is designed as a **portfolio project for Data Analytics / Business Analytics / SQL roles**.

# 🔍 Key SQL Concepts Demonstrated

## 1. JSON Data Handling

Product attributes are stored in a JSON column:

```sql
ALTER TABLE store_sales
ADD COLUMN product_attributes JSON;
```

Example JSON:

```json
{
  "color": "blue",
  "size": "M",
  "material": "cotton"
}
```

The project demonstrates:

* `JSON_EXTRACT()`
* JSON path expressions
* `->>` operator
* `JSON_CONTAINS_PATH()`

Example:

```sql
SELECT sale_id,
       product_attributes,
       JSON_EXTRACT(product_attributes, '$.color') AS color,
       product_attributes->>'$.size' AS size
FROM store_sales
WHERE product_attributes IS NOT NULL;
```

# 📝 4. Sales Audit Logging

An audit table is created to track price changes:

```sql
CREATE TABLE sales_audit_log (
    log_id INT AUTO_INCREMENT PRIMARY KEY,
    sale_id INT,
    action_type VARCHAR(20),
    old_price DECIMAL(10,2),
    new_price DECIMAL(10,2),
    changed_at DATETIME
);
```

A trigger automatically records price changes.

```sql
CREATE TRIGGER before_price_update
BEFORE UPDATE ON store_sales
FOR EACH ROW
```

The trigger captures:

* Sale ID
* Action type
* Previous price
* New price
* Timestamp

This is useful for demonstrating **data auditing and database automation**.

# 🔄 5. Transactions

The project demonstrates transaction control using:

```sql
START TRANSACTION;
COMMIT;
ROLLBACK;
SAVEPOINT;
ROLLBACK TO;
```

### Example

A quantity update and return transaction is committed:

```sql
START TRANSACTION;

UPDATE store_sales
SET quantity = quantity - 1
WHERE sale_id = 3;

INSERT INTO returns
(return_id, sale_id, return_reason, refund_amount)
VALUES
(6, 3, 'Customer changed mind', 2499.00);

COMMIT;
```

The project also demonstrates how `ROLLBACK` can undo an uncommitted change.

---

# 📍 6. SAVEPOINT

The project demonstrates partial rollback using a savepoint:

```sql
START TRANSACTION;

UPDATE store_sales
SET price = 600
WHERE sale_id = 1;

SAVEPOINT after_price_change;

UPDATE store_sales
SET quantity = 100
WHERE sale_id = 1;

ROLLBACK TO after_price_change;

COMMIT;
```

This demonstrates how a transaction can retain some changes while undoing others.

# 📊 7. Category-Wise Revenue Analysis

Conditional aggregation is used to calculate revenue by product category:

```sql
SELECT
    employee_name,
    SUM(CASE
        WHEN category = 'Clothing'
        THEN price * quantity ELSE 0
    END) AS Clothing_Revenue,

    SUM(CASE
        WHEN category = 'Footwear'
        THEN price * quantity ELSE 0
    END) AS Footwear_Revenue,

    SUM(CASE
        WHEN category = 'Accessories'
        THEN price * quantity ELSE 0
    END) AS Accessories_Revenue

FROM store_sales
GROUP BY employee_name;
```

This produces an employee-level category revenue analysis.

# ⚡ 8. SQL Query Optimization

The project demonstrates how query structure can affect index usage.

An index is created:

```sql
CREATE INDEX idx_city_category
ON store_sales(city, category);
```

### Less index-friendly approach

```sql
SELECT *
FROM store_sales
WHERE YEAR(sales_date) = 2026;
```

### More index-friendly approach

```sql
SELECT *
FROM store_sales
WHERE sales_date BETWEEN '2026-01-01'
                     AND '2026-12-31';
```

The project also demonstrates the impact of wildcard searches:

```sql
LIKE '%shirt'
```

versus:

```sql
LIKE 'shirt%'
```

The purpose is to understand how query design can influence database performance.

# 🧠 11. Subqueries

The project uses subqueries to identify employees associated with different product categories.

### Employees involved in Clothing and Footwear

```sql
SELECT DISTINCT e.employee_name
FROM store_sales s
JOIN employees e
    ON s.employee_id = e.employee_id
WHERE s.category = 'Clothing'
AND e.employee_name IN (
    SELECT e2.employee_name
    FROM store_sales s2
    JOIN employees e2
        ON s2.employee_id = e2.employee_id
    WHERE s2.category = 'Footwear'
);
```

### Employees involved in Clothing but not Accessories

```sql
SELECT DISTINCT e.employee_name
FROM store_sales s
JOIN employees e
    ON s.employee_id = e.employee_id
WHERE s.category = 'Clothing'
AND e.employee_name NOT IN (
    SELECT e2.employee_name
    FROM store_sales s2
    JOIN employees e2
        ON s2.employee_id = e2.employee_id
    WHERE s2.category = 'Accessories'
);
```
